1. Как работает ThreadLocal внутри приложения?

Объект ThreadLocal предоставляет так называемые потоко-локальные переменные. В классическом веб-приложении на Java Spring Boot (использующем встроенный сервер Tomcat) каждый входящий HTTP-запрос обрабатывается в отдельном изолированном потоке из пула потоков сервера.

Под капотом ThreadLocal хранит данные в специальной хэш-таблице, где ключом является текущий выполняющийся поток.
Когда запрос от пользователя поступает в приложение:

    Выделенный поток берет этот запрос на обработку.

    Мы записываем роль текущего пользователя СУБД в ThreadLocal.

    Любой класс (сервис, репозиторий, фабрика), который будет вызван в рамках этого же потока, может мгновенно прочитать роль из ThreadLocal без необходимости передавать её аргументом через все методы.

Важная деталь: Потоки в Tomcat используются повторно (после завершения запроса поток возвращается в пул). Если не очистить данные из ThreadLocal в конце запроса, следующий пользователь, которому достанется этот же поток, случайно получит чужие права СУБД. Именно поэтому мы очищаем контекст в методе afterCompletion интерцептора.
2. Как RoutingMongoDatabaseFactory взаимодействует с репозиториями?

Spring Data MongoDB строит репозитории (интерфейсы, наследующие MongoRepository) в виде динамических прокси-объектов во время запуска приложения. Внутри эти прокси-объекты используют стандартный бин MongoTemplate для выполнения всех физических операций с MongoDB.

Связующим звеном здесь выступает MongoDatabaseFactory :  

    Бин MongoTemplate создается на основе переданного ему MongoDatabaseFactory.  

    Когда репозиторий вызывает, например, метод findAll(), он делегирует выполнение MongoTemplate.  

    MongoTemplate обращается к MongoDatabaseFactory и вызывает метод getMongoDatabase(), чтобы получить объект подключения к конкретной базе данных.

    Поскольку наша фабрика RoutingMongoDatabaseFactory объявлена как @Primary, именно она перехватывает этот вызов. Она считывает активную роль из ThreadLocal и возвращает MongoDatabase из пула соединений, настроенного для этой роли.  

Таким образом, для репозиториев переключение контекста происходит абсолютно незаметно.
3. Какое место занимает интерцептор и нужен ли Spring Security?

Для реализации вашей задачи Spring Security использовать не нужно. В учебных целях и для изоляции прав на уровне базы данных это только добавило бы лишней сложности.

Интерцепторы (HandlerInterceptor) являются стандартной частью веб-архитектуры Spring MVC и отлично работают без Spring Security. Интерцептор встраивается непосредственно в цепочку обработки HTTP-запросов DispatcherServlet.

Цепочка обработки выглядит следующим образом:

    Браузер отправляет HTTP-запрос (например, POST /dashboard/deliveries/create).

    DispatcherServlet принимает запрос и находит нужный контроллер.

    Перед запуском метода контроллера вызывается метод preHandle() нашего интерцептора. Он заглядывает в HTTP-сессию, достает оттуда роль пользователя и сохраняет ее в ThreadLocal.

    Выполняется метод контроллера (вызывает репозитории, данные запрашиваются из базы через роутинг-фабрику).  

    Контроллер возвращает имя HTML-шаблона Thymeleaf, и происходит рендеринг страницы.

    После того как страница полностью сформирована и отправлена пользователю, вызывается метод afterCompletion() интерцептора. Он очищает ThreadLocal, предотвращая утечку данных между потоками СУБД.

4. Как GlobalDatabaseExceptionHandler встраивается в Thymeleaf?

При попытке выполнить операцию, на которую у текущего подключения нет прав в MongoDB, драйвер выбрасывает исключение со специфическим кодом ошибки (например, код 13 — Unauthorized). Spring оборачивает его в UncategorizedMongoDbException.  

Глобальный обработчик @ControllerAdvice перехватывает это исключение, возникшее в методах контроллера :  

    Обработчик формирует понятный текст ошибки.  

    Вместо того чтобы просто отобразить пустую страницу ошибки, мы хотим вернуть пользователя на рабочую панель (/dashboard) и показать сообщение там.  

    Для этого используется механизм RedirectAttributes.addFlashAttribute("databaseError", message). Spring временно сохраняет это сообщение в HTTP-сессии.

    Происходит перенаправление (редирект) браузера на эндпоинт GET /dashboard.

    При обработке этого GET-запроса Spring автоматически извлекает сообщение из flash-атрибутов и помещает его в стандартную модель Thymeleaf.

    В HTML-шаблоне Thymeleaf мы ловим эту переменную с помощью простого условия :
    HTML

    <div th:if="${databaseError}" class="alert alert-danger" th:text="${databaseError}"></div>

Использование Post-Redirect-Get паттерна гарантирует, что при случайном обновлении страницы (F5) в браузере не произойдет повторной отправки несанкционированного POST-запроса.

6. Как контроллеры работают с сессией и что ей управляет?

Сессией управляет ваш Servlet-контейнер (встроенный Tomcat). При первом обращении пользователя сервер создает уникальный идентификатор сессии и передает его клиенту в куках под именем JSESSIONID (или SESSION). При каждом последующем запросе браузер передает эту куку обратно, позволяя серверу распознать пользователя.

В коде контроллера работа с сессией реализуется предельно просто — достаточно объявить HttpSession аргументом метода :
Java

@PostMapping("/auth/login")
public String login(@RequestParam String username, @RequestParam String password, HttpSession session) {
    // 1. Проверяем пользователя по коллекции в БД с помощью гостевого подключения
    // 2. Определяем его прикладную роль (например, SUPPLIER)
    
    // 3. Сохраняем роль в HTTP-сессию
    session.setAttribute("user_role", RoutingContext.Role.SUPPLIER);
    
    return "redirect:/dashboard";
}

@PostMapping("/auth/logout")
public String logout(HttpSession session) {
    // Стираем сессию при выходе
    session.invalidate();
    return "redirect:/login";
}

Spring автоматически подставит объект сессии текущего пользователя в метод.
7. Где конструировать запросы агрегации и как к ним обращаться?

Поскольку интерфейсы MongoRepository не предназначены для написания тяжелых многостадийных агрегаций, вам нужно использовать MongoTemplate напрямую.

Для соблюдения чистоты архитектуры лучше всего создать отдельный сервисный класс для бизнес-аналитики — например, WarehouseAnalyticsService :
Java

package com.example.mongo10web.service;

import org.bson.Document;
import org.springframework.data.mongodb.core.MongoTemplate;
import org.springframework.data.mongodb.core.aggregation.Aggregation;
import org.springframework.stereotype.Service;
import java.util.List;

@Service
public class WarehouseAnalyticsService {

    private final MongoTemplate mongoTemplate;

    // Внедряем MongoTemplate, который неявно будет использовать нашу фабрику-маршрутизатор
    public WarehouseAnalyticsService(MongoTemplate mongoTemplate) {
        this.mongoTemplate = mongoTemplate;
    }

    public List<Document> getCategoryDeliveryVolumes() {
        Aggregation aggregation = Aggregation.newAggregation(
            // Описание стадий агрегации ($lookup, $group и т.д.)
        );
        return mongoTemplate.aggregate(aggregation, "deliveries", Document.class).getMappedResults();
    }
}

Как обращаться из контроллера:
Ваш новый WarehouseWebController будет внедрять этот сервис через конструктор вместе с обычными репозиториями :
Java

@Controller
@RequestMapping("/dashboard")
public class WarehouseWebController {

    private final WarehouseAnalyticsService analyticsService;
    private final ProductRepository productRepository;

    public WarehouseWebController(WarehouseAnalyticsService analyticsService, ProductRepository productRepository) {
        this.analyticsService = analyticsService;
        this.productRepository = productRepository;
    }

    @GetMapping("/analytics")
    public String showAnalytics(Model model) {
        // Запрос выполнится под ролью текущего пользователя в потоке!
        List<Document> report = analyticsService.getCategoryDeliveryVolumes();
        model.addAttribute("reportData", report);
        return "analytics-dashboard";
    }
}

Такой подход разделяет CRUD-операции репозиториев и сложную аналитику сервисов, сохраняя код легко читаемым и расширяемым.

Анализ проблем вашего текущего кода

    Причина бесконечной переадресации (Circular Redirect):
    В вашей текущей конфигурации кастомный интерцептор RoleRoutingInterceptor перехватывает все входящие запросы. Когда неавторизованный пользователь открывает страницу /dashboard, интерцептор видит отсутствие роли и перенаправляет его на /login. Но так как /login — это тоже HTTP-запрос, интерцептор перехватывает его, снова видит отсутствие роли и перенаправляет на /login. Возникает бесконечный цикл.
    Решение: Использование Spring Security полностью решает эту проблему за счет зрелого фильтра безопасности, который автоматически умеет исключать страницу входа и статические ресурсы из проверок.

    Проблема авторизации (Chicken-and-Egg):
    Чтобы проверить логин и пароль пользователя по базе данных, нам нужно сделать к ней запрос. Но чтобы сделать запрос к базе данных, нам нужно знать роль пользователя для выбора подключения.
    Решение: Использование специального «гостевого» (GUEST) пула соединений СУБД, который имеет доступ только на чтение коллекции users в вашей базе данных food_shop_storage. Все остальные коллекции для него закрыты.

Шаг 3. Реализация сущности и репозитория пользователя

Создайте класс User :
Java

package com.example.mongo10web.model;

import org.springframework.data.annotation.Id;
import org.springframework.data.mongodb.core.mapping.Document;

@Document(collection = "users")
public class User {
    @Id
    private String id;
    private String username;
    private String password;
    private String role; // "SUPPLIER", "STOREKEEPER", "MANAGER"

    // Геттеры, сеттеры, конструкторы

@Service

    public MongoUserDetailsService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {

        if (user == null) {
            throw new UsernameNotFoundException("Пользователь не найден: " + username);
        }

               .username(user.getUsername())
               .password(user.getPassword())
               .roles(user.getRole()) 
               .build();
    }
}

Шаг 5. Конфигурация Spring Security (SecurityConfig)

Spring Security возьмет на себя обработку входа, выхода и защиту эндпоинтов. Удалите ваш кастомный RoleRoutingInterceptor и класс WebMvcConfig — они больше не понадобятся.
Java

package com.example.mongo10web.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
           .csrf(csrf -> csrf.disable()) // Отключаем CSRF для упрощения локальной разработки формы
           .authorizeHttpRequests(auth -> auth
               .requestMatchers("/login", "/css/**", "/js/**", "/error").permitAll()
               .anyRequest().authenticated()
            )
           .formLogin(form -> form
               .loginPage("/login")
               .loginProcessingUrl("/auth/login") // Спринг обработает POST-запрос авторизации сам
               .defaultSuccessUrl("/dashboard", true)
               .failureUrl("/login?error=true")
               .permitAll()
            )
           .logout(logout -> logout
               .logoutUrl("/auth/logout")
               .logoutSuccessUrl("/login?logout=true")
               .invalidateHttpSession(true)
               .deleteCookies("JSESSIONID")
               .permitAll()
            );

        return http.build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

Шаг 6. Обновление RoutingMongoDatabaseFactory

Теперь нам больше не нужно хранить роли в кастомной ThreadLocal сессии. Spring Security делает это автоматически в безопасном системном контексте SecurityContextHolder. Изменим логику фабрики :
Java

package com.example.mongo10web.config;

import com.mongodb.client.ClientSession;
import com.mongodb.client.MongoDatabase;
import org.springframework.dao.DataAccessException;
import org.springframework.dao.support.PersistenceExceptionTranslator;
import org.springframework.data.mongodb.MongoDatabaseFactory;
import org.springframework.data.mongodb.core.MongoExceptionTranslator;
import org.springframework.security.authentication.AnonymousAuthenticationToken;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.security.core.GrantedAuthority;
import com.mongodb.ClientSessionOptions;

import java.util.Map;

public class RoutingMongoDatabaseFactory implements MongoDatabaseFactory {

    private final Map<String, MongoDatabaseFactory> factories;
    private final PersistenceExceptionTranslator exceptionTranslator = new MongoExceptionTranslator();

    public RoutingMongoDatabaseFactory(Map<String, MongoDatabaseFactory> factories) {
        this.factories = factories;
    }

    private MongoDatabaseFactory getVisibleFactory() {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        
        // Если пользователь не авторизован (например, идет процесс логина), используем GUEST-подключение
        if (auth == null ||!auth.isAuthenticated() || auth instanceof AnonymousAuthenticationToken) {
            return factories.get("GUEST");
        }

        // Получаем роль из SecurityContext
        String role = auth.getAuthorities().stream()
               .map(GrantedAuthority::getAuthority)
               .findFirst()
               .orElse("ROLE_GUEST")
               .replace("ROLE_", ""); // Превращаем ROLE_SUPPLIER в SUPPLIER

        return factories.getOrDefault(role, factories.get("GUEST"));
    }

    @Override
    public MongoDatabase getMongoDatabase() throws DataAccessException {
        return getVisibleFactory().getMongoDatabase();
    }

    @Override
    public MongoDatabase getMongoDatabase(String dbName) throws DataAccessException {
        return getVisibleFactory().getMongoDatabase(dbName);
    }

    @Override
    public PersistenceExceptionTranslator getExceptionTranslator() {
        return this.exceptionTranslator;
    }

    @Override
    public ClientSession getSession(ClientSessionOptions options) throws DataAccessException {
        return getVisibleFactory().getSession(options);
    }

    @Override
    public MongoDatabaseFactory withSession(ClientSession session) {
        return getVisibleFactory().withSession(session);
    }
}

import com.example.mongo10web.model.Category;

import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.*;

import java.time.Instant;

@Controller
public class WarehouseWebController {

    private final ProductRepository productRepository;
    private final DeliveryRepository deliveryRepository;
    private final CategoryRepository categoryRepository;

    public WarehouseWebController(ProductRepository productRepository,
                                  DeliveryRepository deliveryRepository,
                                  CategoryRepository categoryRepository) {
        this.productRepository = productRepository;
        this.deliveryRepository = deliveryRepository;
        this.categoryRepository = categoryRepository;
    }

    @GetMapping("/login")
    public String loginPage() {
        return "login";
    }

    @GetMapping("/dashboard")
    public String dashboard(Model model) {
        // Запросы выполняются под СУБД-ролью текущего авторизованного пользователя
        model.addAttribute("products", productRepository.findAll());
        model.addAttribute("deliveries", deliveryRepository.findAll());
        model.addAttribute("categories", categoryRepository.findAll());

        // Заготовки для форм создания
        model.addAttribute("newProduct", new Product());
        model.addAttribute("newDelivery", new Delivery());
        model.addAttribute("newCategory", new Category());

        return "dashboard";
    }

    @PostMapping("/products/create")
    public String createProduct(@ModelAttribute Product product) {
        productRepository.save(product);
        return "redirect:/dashboard";
    }

    @PostMapping("/products/delete/{id}")
    public String deleteProduct(@PathVariable String id) {
        productRepository.deleteById(id);
        return "redirect:/dashboard";
    }

    // --- CRUD ДЛЯ ПОСТАВОК (DELIVERIES) ---
    @PostMapping("/deliveries/create")
    public String createDelivery(@ModelAttribute Delivery delivery) {
        // Установка значений по умолчанию на стороне сервера
        delivery.setCreatedAt(Instant.now());
        delivery.setStatus("CREATED");
        
        deliveryRepository.save(delivery);
        return "redirect:/dashboard";
    }

    @PostMapping("/deliveries/update-status/{id}")
    public String updateDeliveryStatus(@PathVariable String id, @RequestParam String status) {
        deliveryRepository.findById(id).ifPresent(delivery -> {
            delivery.setStatus(status);
            deliveryRepository.save(delivery);
        });
        return "redirect:/dashboard";
    }

    @PostMapping("/deliveries/delete/{id}")
    public String deleteDelivery(@PathVariable String id) {
        deliveryRepository.deleteById(id);
        return "redirect:/dashboard";
    }

    // --- CRUD ДЛЯ КАТЕГОРИЙ (CATEGORIES) ---
    @PostMapping("/categories/create")
    public String createCategory(@ModelAttribute Category category) {
        categoryRepository.save(category);
        return "redirect:/dashboard";
    }

    @PostMapping("/categories/delete/{id}")
    public String deleteCategory(@PathVariable String id) {
        categoryRepository.deleteById(id);
        return "redirect:/dashboard";
    }

Давайте разберем причины возникших у вас ошибок и пошагово исправим проект, используя правильные имена классов, моделей и репозиториев из вашего проекта.
Почему возникают текущие ошибки?

    Бесконечный цикл перенаправлений (Circular Redirect):
    Это происходит потому, что в Spring Security эндпоинт /login по умолчанию защищен так же, как и все остальные страницы. Когда неавторизованный пользователь пытается зайти на /dashboard, Spring Security перенаправляет его на /login. Но при попытке открыть /login система безопасности видит, что пользователь не авторизован, и снова перенаправляет его на /login.
    Решение: Необходимо явно указать в конфигурации безопасности, что доступ к странице /login разрешен абсолютно всем (.permitAll()). Также обязательно полностью удалите старый интерцептор RoleRoutingInterceptor и класс WebMvcConfig из вашего проекта. Они больше не нужны, так как Spring Security берет управление сессиями и защитой страниц на себя.

    Появление стандартного окна авторизации и генерация пароля в консоли:
    Spring Boot генерирует случайный пароль в консоли только тогда, когда он не может обнаружить в контексте приложения зарегистрированный бин UserDetailsService. Если вы создали этот класс, но Spring его не видит, проверьте:

        Находится ли класс в том же базовом пакете (или его подпакетах), что и главный класс приложения (обычно это com.example.mongo10web).

        Помечен ли класс аннотацией @Service или @Component.
        Если эти условия не выполнены, Spring Security считает, что кастомного источника пользователей нет, и включает стандартную in-memory защиту со сгенерированным паролем user.

Шаг 3. Реализация сервиса аутентификации

Создайте класс MongoUserDetailsService в пакете com.example.mongo10web.security. Аннотация @Service обязательна, чтобы Spring Security отключил стандартного пользователя user.
Java

package com.example.mongo10web.security;

import com.example.mongo10web.model.User;
import com.example.mongo10web.repository.UserRepository;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.stereotype.Service;

@Service
public class MongoUserDetailsService implements UserDetailsService {

    private final UserRepository userRepository;

    public MongoUserDetailsService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        // Запрос выполнится через гостевое (GUEST) подключение к СУБД
        User user = userRepository.findByUsername(username);
        if (user == null) {
            throw new UsernameNotFoundException("Пользователь не найден: " + username);
        }

        return org.springframework.security.core.userdetails.User.builder()
               .username(user.getUsername())
               .password(user.getPassword())
               .roles(user.getRole()) // Spring Security автоматически добавит префикс "ROLE_"
               .build();
    }
}

Шаг 4. Настройка конфигурации безопасности (Без циклической переадресации)

Создайте класс SecurityConfig в пакете com.example.mongo10web.config. Мы разрешим неавторизованный доступ только к странице входа /login и статическим ресурсам, а также настроим обработку логина.
Java

package com.example.mongo10web.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
           .csrf(csrf -> csrf.disable()) // Отключаем CSRF для удобства работы с Thymeleaf-формами на локальном хосте
           .authorizeHttpRequests(auth -> auth
                // Разрешаем всем доступ к странице входа и ресурсам, чтобы избежать бесконечного редиректа
               .requestMatchers("/login", "/css/**", "/js/**", "/error").permitAll()
                // Все остальные запросы требуют обязательной авторизации
               .anyRequest().authenticated()
            )
           .formLogin(form -> form
               .loginPage("/login") // Наш кастомный эндпоинт для отображения страницы входа
               .loginProcessingUrl("/auth/login") // POST-эндпоинт, который Spring Security обработает сам
               .defaultSuccessUrl("/dashboard", true)
               .failureUrl("/login?error=true")
               .permitAll()
            )
           .logout(logout -> logout
               .logoutUrl("/auth/logout")
               .logoutSuccessUrl("/login?logout=true")
               .invalidateHttpSession(true)
               .deleteCookies("JSESSIONID")
               .permitAll()
            );

        return http.build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

Шаг 5. Обновление динамической фабрики подключений

Класс RoutingMongoDatabaseFactory больше не зависит от интерцепторов и сессий Servlet API. Теперь он напрямую и безопасно считывает роль из контекста Spring Security:
Java

package com.example.mongo10web.config;

import com.mongodb.client.ClientSession;
import com.mongodb.client.MongoDatabase;
import org.springframework.dao.DataAccessException;
import org.springframework.dao.support.PersistenceExceptionTranslator;
import org.springframework.data.mongodb.MongoDatabaseFactory;
import org.springframework.data.mongodb.core.MongoExceptionTranslator;
import org.springframework.security.authentication.AnonymousAuthenticationToken;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.security.core.GrantedAuthority;
import com.mongodb.ClientSessionOptions;

import java.util.Map;

public class RoutingMongoDatabaseFactory implements MongoDatabaseFactory {

    private final Map<String, MongoDatabaseFactory> factories;
    private final PersistenceExceptionTranslator exceptionTranslator = new MongoExceptionTranslator();

    public RoutingMongoDatabaseFactory(Map<String, MongoDatabaseFactory> factories) {
        this.factories = factories;
    }

    private MongoDatabaseFactory getVisibleFactory() {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();

        // Если пользователь еще не вошел (например, Спринг пытается найти его в БД при логине)
        if (auth == null ||!auth.isAuthenticated() || auth instanceof AnonymousAuthenticationToken) {
            return factories.get("GUEST");
        }

        // Извлекаем роль и приводим к формату ключа мапы ("MANAGER", "STOREKEEPER", "SUPPLIER")
        String role = auth.getAuthorities().stream()
               .map(GrantedAuthority::getAuthority)
               .findFirst()
               .orElse("ROLE_GUEST")
               .replace("ROLE_", "");

        return factories.getOrDefault(role, factories.get("GUEST"));
    }

    @Override
    public MongoDatabase getMongoDatabase() throws DataAccessException {
        return getVisibleFactory().getMongoDatabase();
    }

    @Override
    public MongoDatabase getMongoDatabase(String dbName) throws DataAccessException {
        return getVisibleFactory().getMongoDatabase(dbName);
    }

    @Override
    public PersistenceExceptionTranslator getExceptionTranslator() {
        return this.exceptionTranslator;
    }

    @Override
    public ClientSession getSession(ClientSessionOptions options) throws DataAccessException {
        return getVisibleFactory().getSession(options);
    }

    @Override
    public MongoDatabaseFactory withSession(ClientSession session) {
        return getVisibleFactory().withSession(session);
    }
}

Ваш MongoRoutingConfig остается прежним, только в factoryMap.put() используйте строковые ключи "GUEST", "SUPPLIER", "STOREKEEPER", "MANAGER".

Существующий ProductController оставьте для обслуживания API эндпоинтов группы /product. А для отрисовки веб-страниц создадим WebController в пакете com.example.mongo10web.controller.

Здесь реализована логика автоматического присвоения текущего времени (Instant.now()) и статуса "CREATED" для создаваемых поставок:
Java

package com.example.mongo10web.controller;

import com.example.mongo10web.model.Category;
import com.example.mongo10web.model.Delivery;
import com.example.mongo10web.model.Product;
import com.example.mongo10web.repository.CategoryRepository;
import com.example.mongo10web.repository.DeliveryRepository;
import com.example.mongo10web.repository.ProductRepository;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.*;

import java.time.Instant;

@Controller
public class WebController {

    private final ProductRepository productRepository;
    private final DeliveryRepository deliveryRepository;
    private final CategoryRepository categoryRepository;

    public WebController(ProductRepository productRepository,
                         DeliveryRepository deliveryRepository,
                         CategoryRepository categoryRepository) {
        this.productRepository = productRepository;
        this.deliveryRepository = deliveryRepository;
        this.categoryRepository = categoryRepository;
    }

    @GetMapping("/login")
    public String loginPage() {
        return "login";
    }

    @GetMapping("/dashboard")
    public String dashboardPage(Model model) {
        // Подгружаем списки из всех трех коллекций СУБД
        model.addAttribute("products", productRepository.findAll());
        model.addAttribute("deliveries", deliveryRepository.findAll());
        model.addAttribute("categories", categoryRepository.findAll());

        // Объекты-пустышки для связывания Thymeleaf-форм (Thymeleaf Form Binding)
        model.addAttribute("newProduct", new Product());
        model.addAttribute("newDelivery", new Delivery());
        model.addAttribute("newCategory", new Category());

        return "dashboard";
    }

    // --- УПРАВЛЕНИЕ ПОСТАВКАМИ (DELIVERIES) ---
    @PostMapping("/deliveries/create")
    public String createDelivery(@ModelAttribute Delivery delivery) {
        // Автоматическое заполнение системных полей на стороне сервера
        delivery.setCreatedAt(Instant.now());
        delivery.setStatus("CREATED");
        
        deliveryRepository.save(delivery);
        return "redirect:/dashboard";
    }

    @PostMapping("/deliveries/delete/{id}")
    public String deleteDelivery(@PathVariable String id) {
        deliveryRepository.deleteById(id);
        return "redirect:/dashboard";
    }

    // --- УПРАВЛЕНИЕ ТОВАРАМИ (PRODUCTS) ---
    @PostMapping("/products/create")
    public String createProduct(@ModelAttribute Product product) {
        productRepository.save(product);
        return "redirect:/dashboard";
    }

    @PostMapping("/products/delete/{id}")
    public String deleteProduct(@PathVariable String id) {
        productRepository.deleteById(id);
        return "redirect:/dashboard";
    }

    // --- УПРАВЛЕНИЕ КАТЕГОРИЯМИ (CATEGORIES) ---
    @PostMapping("/categories/create")
    public String createCategory(@ModelAttribute Category category) {
        categoryRepository.save(category);
        return "redirect:/dashboard";
    }

    @PostMapping("/categories/delete/{id}")
    public String deleteCategory(@PathVariable String id) {
        categoryRepository.deleteById(id);
        return "redirect:/dashboard";
    }
}

Почему не работало? Главные архитектурные ошибки в коде

    Spring Security полностью игнорировался Спрингом (и выдавал дефолтное окно с паролем в консоли):
    В вашем классе SecurityConfig отсутствовали аннотации @Configuration и @EnableWebSecurity! Без них Spring Boot не знал, что этот класс настраивает безопасность. Он применял дефолтные настройки безопасности (HTTP Basic с логином user и паролем в консоли), защищая в том числе эндпоинт /login.

    Циклическое перенаправление (Circular Redirect):
    Поскольку Spring Security работал по дефолтной схеме, он блокировал доступ к вашей странице /login. Неавторизованный запрос на /dashboard перенаправлялся на /login, но так как /login тоже требовал авторизации, происходил повторный редирект на /login — и так до бесконечности. Кроме того, в вашем WebController полностью отсутствовал метод-обработчик GET /login.

    Почему не удавалось войти с «захешированным» паролем (Проблема коллекции User):
    В Spring Data MongoDB класс User по умолчанию проецируется в коллекцию user (в единственном числе), так как вы не указали имя коллекции в аннотации @Document. Если вы вручную создали коллекцию users (во множественном числе) и добавили документ туда, то ваш userRepository.findByUsername() искал запись в пустой коллекции user и возвращал null.

    Проблема подключения UNAUTHORIZED при включенном СУБД-аутентификаторе (--auth):
    Если на сервере MongoDB включена авторизация, анонимное (без логина и пароля) подключение СУБД для роли UNAUTHORIZED  не сможет даже прочитать коллекцию пользователей для проверки пароля, возвращая ошибку доступа (Unauthorized 13).
